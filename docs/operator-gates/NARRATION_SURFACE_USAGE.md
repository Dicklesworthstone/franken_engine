# Narration Surface Usage

Operator runbook for the Track X proactive incident narration surface.
**Read the safety boundary section before you read anything else.**

## The safety boundary (read first)

**Narration is signed evidence, not free-form analysis.**

The narration text the runtime emits for a guardplane boundary crossing
is a typed, content-addressed, replay-anchored artifact. Its
`explanation_id` is a hash of its core fields
(`DecisionExplanation::compute_id`); its replay obligation is that
re-running the constrained-grammar generator against the same inputs
produces the **byte-identical** text.

This has four hard operator consequences:

1. **Operators MUST NOT edit the narration text.** Any
   character-level edit — fixing a typo, smoothing a phrase,
   shortening for an exec summary, even re-wrapping lines —
   invalidates the signature and breaks the replay obligation. The
   downstream Track X.3 gate (`run_rgc_incident_narration.sh`) will
   catch it; do not bypass that gate.
2. **Operators MUST NOT paste narration text into a free-form
   incident report.** Quote-with-attribution to the
   `explanation_id` is the only correct surface for inclusion. The
   incident-report tool must reference the receipt, not embed the
   text.
3. **Operators MAY add commentary.** Commentary lives in its own
   typed surface (the incident report body, the comments thread on
   the bead, the post-mortem doc) and is clearly separated from the
   signed narration. Commentary is never re-signed by the engine.
4. **Operators MAY NOT use narration to "explain" decisions the
   engine did not actually make.** Narration is generated by the
   engine for boundary crossings the guardplane actually observed.
   Backfilling a narration after the fact — even with all the
   correct inputs — is not the same operation. The replay gate
   distinguishes the two.

If the operator workflow contains "edit the narration before
shipping the report," that workflow is wrong. The narration is the
evidence; the report is built around it, not on top of it.

## What the narration surface emits

For every guardplane boundary crossing, the runtime produces a
`DecisionExplanation` carrying:

| Field | What it is | How operators use it |
|---|---|---|
| `explanation_id` | Content-addressed hash (`expl-<16-hex>`) computed from `(decision_id, epoch, domain)`. | Stable id — cite this in any incident report or follow-up bead. The hash is the join key between the narration, the receipt, the bundle, and any downstream artifact. |
| `decision_id` | The decision being explained. | Join key into the decision ledger. Always cite alongside `explanation_id`. |
| `epoch` | `SecurityEpoch` at decision time. | Replay anchor — must match the receipt and the bundle. |
| `domain` | `DecisionDomain`: `LaneRouting` / `Fallback` / `Optimization` / `Security` / `Governance`. | First sort key when triaging a batch of narrations. |
| `verbosity` | `VerbosityLevel`: `Minimal` / `Standard` (default) / `GalaxyBrain`. | Determines which extended fields are populated. |
| `regime` | The regime label active at decision time. | Cite when the narration is for a regime-conditional decision. |
| `equations` | `Vec<GoverningEquation>` — the model(s) that drove the decision, with substituted parameters and computed results. | The "why" of the decision in mathematical form. Read `GoverningEquation::plain_language()` for the rendered prose. |
| `chosen_action` + `chosen_loss_millionths` | The selected action + its expected loss. | The "what" of the decision. |
| `rationale` | Plain-language rationale (English text generated by the constrained grammar). | The line operators most often want to quote. **Quote by reference, not by copy-paste.** |
| `alternatives` | `Vec<ExplainedAlternative>` — rejected actions with `RejectionReason`. | The "what else was considered." |
| `constraints` | (Standard / GalaxyBrain) Active constraints + `binding: bool`. | If `has_binding_constraint()` is true, the decision was forced by a constraint, not chosen by score. |
| `risk_breakdown` | (Standard / GalaxyBrain) Per-factor risk decomposition. | The "where the risk score came from." `total_risk_millionths()` re-derives the total. |
| `counterfactuals` | (GalaxyBrain only) Outcomes under alternative actions. | The "what would have happened if" record. |
| `posterior_millionths` | (GalaxyBrain only) Posterior over risk factors. | The Bayesian state at decision time. |
| `confidence_millionths` | (GalaxyBrain only) Confidence in the decision (0..1_000_000). | Read before quoting the rationale — low-confidence rationale should NOT be quoted without the confidence value. |

The constrained grammar maps typed `(decision input + policy +
posterior + action)` fields into `NarrativeToken` values and only
then renders bytes. Replays compare the rendered bytes, not an
operator-edited paragraph.

The `VerbosityLevel` is set at generation time and cannot be raised
retroactively. A `Minimal` narration cannot be "expanded" into a
`Standard` one after the fact; doing so produces a different
`explanation_id` and is a new artifact, not an upgrade of the old.

## The operator workflow

### 1. A boundary crossing fires; a narration appears

The narration arrives via the operator surface (TUI panel, CLI tail,
incident channel webhook — exact surface deferred). Each narration
appears with its `explanation_id`, `decision_id`, `domain`, and the
`one_line_summary()`. The one-line summary is the right thing to put
in a paging-tier alert; the full narration belongs in the followup
ticket.

### 2. Triage the narration

Read in this order:

1. `domain` — what kind of decision is this?
2. `chosen_action` + `chosen_loss_millionths` — what did the engine
   pick, and at what cost?
3. `has_binding_constraint()` — was this a forced choice?
4. `rationale` — the English line.
5. `equations[*].plain_language()` — the math behind the line.
6. `alternatives` — what else was on the table?
7. (Standard / GalaxyBrain) `risk_breakdown` and `constraints`.
8. (GalaxyBrain only) `counterfactuals`, `posterior_millionths`,
   `confidence_millionths`.

If the narration's `domain` is `Security` or `Fallback`, the boundary
crossing is operator-actionable by default — see step 3. For
`LaneRouting`, `Optimization`, or `Governance`, the narration is
typically informational unless a downstream gate also fired.

### 3. Verify replay byte-identity BEFORE acting

For any narration that will feed into an external decision (an
incident report, a customer communication, a policy rollback), run
the X.3 replay gate before acting on it:

```bash
runbooks/scripts/run_rgc_incident_narration.sh <explanation_id>
```

The gate re-runs the constrained-grammar generator against the same
inputs and asserts byte-identical narration text plus a matching
signature. If the gate fails, the narration is corrupt — escalate
to a Track X maintainer immediately; do NOT use the text. (See
"What NOT to do" below.)

### 4. Cite, do not copy

In every downstream artifact (bead, incident report, post-mortem,
customer message), cite the narration by `explanation_id` +
`decision_id` + the relevant excerpt. The incident-report tool MUST
support "embed by reference" — operators must not be forced to
copy-paste.

A correct citation looks like:

```text
Narration: expl-c3f2a1...4d8a (decision dec-2026-05-21-...), domain=security.
The runtime narration states (verbatim, byte-identical to replay):

> [security] dec-2026-05-21-... → quarantine (loss=180000,
> regime=elevated): capability narrowing predicate exceeded; the
> binding constraint is the per-tenant capability-grant rate gate.

Source bundle: ire-<hash>. Verbosity: standard. Confidence: n/a
(not GalaxyBrain).
```

An incorrect citation embeds the narration text into a paragraph
that was written by the operator, with the narration's text edited
to flow with the surrounding prose. That is forbidden.

### 5. Attach operator commentary on the side

If the operator wants to add interpretation ("we believe this was
triggered by deploy 42, see..."), the commentary goes in the
*incident report body* or the *bead description* — separated from
the verbatim narration block. The verbatim narration block is the
signed evidence; the commentary is the operator's reasoning. The
two MUST be visually and structurally distinct in any downstream
artifact.

## What NOT to do

- **Do NOT edit the narration text.** Any character change breaks
  the replay obligation and the signature. Typos in the narration
  are bugs to file against the constrained grammar (Track X.1), not
  things to fix at the report level.
- **Do NOT paraphrase the narration in a quote that claims to be the
  narration.** Paraphrase is fine — but it MUST be clearly labeled
  as operator commentary, not as the narration itself.
- **Do NOT translate the narration to another language and then sign
  the translation as if it were the original.** The constrained
  grammar emits one language per generation; translation produces a
  derivative artifact that is not replay-anchored by the X.3 gate.
- **Do NOT raise the verbosity after the fact.** A `Minimal`
  narration cannot become `Standard` by re-rendering. To get a
  higher-verbosity narration, the *decision* must be re-replayed
  with a higher `VerbosityLevel` configured — and the output is a
  new `explanation_id`, not an "expanded" version of the old.
- **Do NOT use narration to explain decisions the engine did not
  make.** Narration is for actual boundary crossings the guardplane
  observed. If an operator wants to explain a hypothetical, they
  use the counterfactual surface (see
  `COUNTERFACTUAL_REPLAY_OPERATOR_SURFACE.md`), and the counterfactual
  output is labeled as such — not as engine narration.
- **Do NOT use narration as the sole basis for an irreversible
  action.** The narration is evidence, not authorization. For
  irreversible actions (e.g., revocations, kill-decisions), require
  a separate signed authorization on top of the narration evidence.
- **Do NOT silence a narration to "reduce noise".** If the
  narration volume is too high, the right fix is at the gate
  threshold (Track X.3) or the verbosity setting — never at the
  operator surface by filtering or dropping individual narrations.
- **Do NOT bypass the X.3 replay gate before quoting a narration in
  an external-facing artifact.** A narration that does not survive
  the byte-identity replay check is corrupt; quoting it in an
  incident report — even one that's internal — propagates the
  corruption.

## When the replay gate fails

If `run_rgc_incident_narration.sh <explanation_id>` fails, the
diagnosis branches on which kind of failure:

| Failure | Likely cause | Operator action |
|---|---|---|
| Signature mismatch, text identical | Key rotation issue, or the receipt was signed by a now-revoked key. | File a Track X bead; do NOT use the narration; check the key revocation ledger. |
| Text differs | Constrained-grammar generator non-determinism, or input drift since the receipt was issued. | P1 bead against bd-cixqu.24.1 (the generator) — this is a contract violation; quarantine the explanation_id until resolved. |
| `decision_id` not found in ledger | The narration is for a decision that was never recorded, or the ledger has been rotated. | File a Track G + Track X bead jointly; treat the narration as unverifiable. |
| Replay artifact bundle missing | The `IncidentReplayBundle` for this `decision_id` is not in storage. | Storage adapter incident — escalate to the storage owner, not Track X. |

In all four cases, do NOT use the narration text in any downstream
artifact until the failure is resolved.

## Cross-cutting rules

- **The `explanation_id` is the join key everywhere.** Bundles,
  receipts, beads, incident reports, post-mortems — all cite by id.
  The text is a renderable view; the id is the artifact.
- **Determinism is a contract, not a goal.** Any non-deterministic
  narration is a Track X.1 bug. Operators who observe
  non-determinism MUST file rather than work around it.
- **Verbosity is set at generation time.** The right verbosity is
  configured per `DecisionDomain` upstream of the operator; the
  operator does not retroactively change it.
- **Constrained grammar means no LLM-in-runtime.** The narration
  text is generated by a deterministic grammar, not a model. Any
  proposal to "improve" the narration by calling out to a language
  model at runtime is rejected on contract grounds — replay
  byte-identity cannot survive a stochastic generator.

## Deferred (out of scope for this runbook)

The X.4 operator surface is implemented incrementally. The following
artifacts are explicitly deferred to follow-up beads under
bd-cixqu.24:

- A `runbooks/scripts/cite_narration.sh` wrapper that takes an
  `explanation_id`, runs the X.3 replay gate, and emits a citation
  block ready to paste into an incident report (with verbatim text,
  bundle id, and signature attestation).
- A frankentui panel for the narration surface (live tail of
  guardplane narrations, filterable by `domain` + `verbosity`, with
  one-click "cite by reference" and an explicit warning when the
  user tries to edit the narration text).
- An incident-report template that uses the narration-by-reference
  primitive and rejects pasted narration text.
- A "narration drift" detector that runs the X.3 replay gate
  proactively (cron) against every narration emitted in the last 24
  hours and pages on the first byte-identity failure.
- Key-rotation UX for the narration-receipt signing key (the
  cryptographic primitives are already in the engine; the
  operator-facing surface is deferred).

Each deferred surface targets the stable artifact contract this
runbook documents; none of them are blockers for landing the
runbook itself.
